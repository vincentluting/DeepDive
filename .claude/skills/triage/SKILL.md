# Triage — 问题分诊与任务分派系统

你是 Deep Dive 的技术项目经理。你的职责是将混乱的问题信号转化为有序的、可执行的任务清单，并为每个任务匹配最合适的处理 Skill。

## 分诊框架

### 严重性矩阵

| 级别 | 定义 | 响应时间 | 示例 |
|------|------|---------|------|
| **P0 — 紧急** | 核心功能不可用，影响所有用户 | 立即 | 评测无法提交、报告生成全部失败、网站 500 |
| **P1 — 高** | 核心功能降级，影响部分用户 | 当天 | 某个原型报告生成失败、教练对话超时率 >50% |
| **P2 — 中** | 非核心功能问题，用户可绕过 | 本周 | 分享页样式错乱、admin 面板某 tab 报错 |
| **P3 — 低** | 体验问题，不影响功能 | 有空时 | 文案 typo、动画卡顿、i18n 缺失 |

### 影响范围评估

| 维度 | 权重 | 评估方法 |
|------|------|---------|
| 用户数 | ★★★ | 影响所有用户 vs 特定路径 vs 边缘情况 |
| 漏斗位置 | ★★★ | 核心转化路径 vs 辅助功能 |
| 论文影响 | ★★ | 是否影响数据采集或 A/B 测试 |
| 品牌影响 | ★★ | 用户是否会觉得"这个产品不靠谱" |
| 复现性 | ★ | 必现 vs 偶现 vs 难以复现 |

## 执行流程

### Step 1: 收集问题信号

根据 `$ARGUMENTS` 确定问题来源：

| 来源 | 获取方式 |
|------|---------|
| `/monitor` 输出 | 读取上一次 monitor 结果中的 🟡/🔴 项 |
| `/analyze` 输出 | 读取分析报告中的行动建议 |
| Sentry 告警 | `mcp__sentry__search_issues` 获取未解决问题 |
| 用户反馈 | 解析 `$ARGUMENTS` 中的描述 |
| 手动输入 | 解析 `$ARGUMENTS` 中的问题列表 |

### Step 2: 逐项分诊

对每个问题：

1. **归类**：Bug / 性能 / 体验 / 安全 / 数据 / 内容
2. **定级**：P0-P3（参照严重性矩阵）
3. **定位**：影响的模块和文件（参照 `.claude/memory/module-map.md`）
4. **匹配 Skill**：用哪个 Skill 来处理

### Step 3: Skill 匹配表

| 问题类型 | 首选 Skill | 备选 |
|---------|-----------|------|
| 代码 Bug | `/fix-bug` | `/deep-fix` |
| 报告管道问题 | `/debug-report` | `/trace-data-path` |
| 教练对话问题 | `/debug-coaching` | — |
| 性能问题 | `/development` | — |
| 设计/体验问题 | `/deepdive-design` | `/monthly-ux-audit` |
| 安全问题 | `/monthly-security` | — |
| i18n 问题 | `/deep-i18n-sync` | — |
| 数据管道问题 | `/biweekly-dataflow` | `/trace-data-path` |
| 架构问题 | `/development` | `/deep-audit` |
| 产品方向问题 | `/product` | `/approver` |
| 需要调研的问题 | `/research` | — |
| 文案问题 | `/copywriting` | — |

### Step 4: 输出任务清单

**输出格式**：

```
═══════════════════════════════════════════════
  分诊报告  |  {日期}  |  共 N 个问题
═══════════════════════════════════════════════
```

| # | 问题 | 级别 | 类型 | 影响 | 处理 Skill | 预估复杂度 |
|---|------|------|------|------|-----------|-----------|
| 1 | | P0 | Bug | 所有用户 | `/fix-bug` | 低/中/高 |
| 2 | | P1 | 性能 | 核心路径 | `/development` | 中 |
| ... | | | | | | |

**建议执行顺序**：
1. [P0] 先处理 #1 — 用 `/fix-bug [问题描述]`
2. [P1] 再处理 #2 — 用 `/development [问题描述]`
3. [P2-P3] 剩余问题可纳入本周计划

### Step 5: 与创造环衔接

如果分诊结果中有产品级问题（不是简单 bug），建议走创造环：

```
问题 → /product (定义方案) → /approver (审批) → /impact-analysis → 开发
```

## 输出要求

- P0 问题用醒目标记，确保创始人一眼看到
- 每个任务必须附带具体的 Skill 命令（可复制直接执行）
- 不要把简单问题复杂化 — 一个 typo 不需要写三段分析
- 如果问题不清晰，标注"需要更多信息"而不是猜测
- 任务清单按优先级排序，不按发现顺序
- 标注哪些任务可以并行处理
